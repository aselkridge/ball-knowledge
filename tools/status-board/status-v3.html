How we get there

the routines, written down
How a change to the game gets ruled and shipped

Show the list, show real options, ship nothing until you pick. The option rounds of 09-10 are the worked example.

  1. Say the medium out loud first: build it, source it, or reuse a device the game already has (DESIGN § 9 and the shipped game are checked before anything is drawn).
  2. The option LIST goes to you before any option is built.
  3. Three or four real options side by side, at the size they will be seen, on the real court, photographed by the game itself under identical conditions, with a recommendation and its reasons after the frames, not before.
  4. Nothing ships until you pick. A direction you approve is not a green light: the sample comes first.
  5. The ruling goes to DESIGN.md the same day with the numbers you picked; the row and the changelog carry it; the check fleet grows a check that asserts it.
  6. Every visual change merges with a before/after from real screenshots, desktop and phone (the compare skill).
How a fact becomes a question in the game

find → prove → merge. Nothing enters questions.js or players.json except through it.

  1. A run gathers candidates into docs/play/data/.
  2. The verify-facts skill reads each claim against its source and gives one of three verdicts: verify, fix, or quarantine. Quarantine never deletes.
  3. tier-sources.py --apply scores the sources. Any Tier 1 gives high confidence; two Tier 2 sources from different publishers also give high; one Tier 2 gives medium.
  4. tables-verify.py then tables-emit.py --apply rebuilds the game files from the tables, which are the real source of truth.
  5. build-volatile-index.py and build-verified-index.py rebuild what the game is allowed to deal.
  6. audit.py is the gate. Old debt passes, new debt fails.
How work gets remembered

A decision or a to-do that is only in chat does not exist.

  1. Anything new (a decision, a bug, a deferral, an idea) becomes a row in TODO.md the same turn it is said; python3 tools/list.py reads the plan, --yours prints what waits on you.
  2. A row leaves only two ways: it shipped and BUILD.md's changelog says so, or it moved to SCRAPPED with a reason.
  3. python3 tools/open-items.py harvests everything still owed from the docs that own it, so prose cannot hide a task.
  4. Every bug gets a verdict out loud: FIXED, FILED with a row number, or RULED.
  5. Rulings go to DESIGN.md. Lessons about working with AI go to AI-LEARNINGS.md. The story goes to MAKING.md. The list board (The Whole List) is republished after any change to the rows or the changelog.
How the board itself is made

Generated from the docs at build time. The list cannot be shorter than the docs; the curated blocks can still go stale, which is what happened between 08-24 and 09-30.

  1. python3 tools/status-board/harvest.py reads TODO.md (every row of the six lists, since 09-30), then V0, BUILD, RESEARCH-BACKLOG, DESIGN and TABLES, and extracts every item.
  2. python3 tools/status-board/build.py renders it into template-v3.html, recomputes the gates, the branch and the 27, inlines the fonts, and refuses to finish if any harvested item is missing from the page.
  3. The curated blocks (right now, your desk, the roadmap, the guides) are the one part written by hand, and every number in them is read from the files at build time.
  4. If something is missing from this board it is missing from the docs, which is a different and more useful problem.

What the words mean

plain language
A card
One question plus its answer, its difficulty, and the source somebody read to prove it.
Dealable
A card the live game is allowed to ask. It needs high confidence AND a recorded date when a person read the source. High confidence alone is not enough, which is how 331 became 298 on 08-06; the pool has since grown to the number on the gate card.
Tier 1 / 2 / 3
How good a source is. Tier 1 is the record of fact, like basketball-reference or the league itself. Tier 2 is reputable but needs a second, independent publisher to agree. Tier 3 is a lead and never ships on its own.
The gate
The rule that stops the game asking a question nobody has checked. It is on.
Stale
A fact that can change, like an active career record. It still ships, but it has to be re-read on a cycle: 180 days normally, 550 days if it is anchored to a season that has ended.
The ratchet
How audit.py works. Existing problems are allowed to pass so old debt does not block every commit, but any NEW problem of the same kind fails.
The twenty
The twenty friends who get the first real invite. They owe you nothing, so the game has to be worth a second session.
The road, list 1
The first list in TODO.md. Its order is the plan; the number on a row is its name and never changes when the row moves.
Row 103
The gameplay rebuild, the umbrella every screen-by-screen ruling since 08-22 lives under: what a player needs to know and do at each moment, and nothing else on the screen.
Method B
The possession the live game plays today: every dead ball opens a setup ritual, defense picks first and visibly, then free moves, one slide, the action. The new rules replace it.
The mock-up
The new possession rules running on the real court behind a switch in the address: ?flow=new against the machine, ?flow=local on one phone. The live game does not know it exists.
The check fleet
The scripts that drive the real game and assert what a change promised; every new check is sabotaged red before it counts, and node tools/gates.mjs runs all of them.
V-number, H-number, S-number
Ids for research and verification jobs. V is verification debt, H is a history deep dive, S is a stats run, Q unblocks a feature, P is a player run, C is a checking task like licensing.
